# Kevin 文章 skill

## 这个 skill 的定位

**记住 Kevin 怎么写，确保 AI 不要写歪。**

不规定段数、图数、结构模板。不写"做这些/禁止这些"的风格规则。
靠四件东西：跨类型的声音特征 + 三种文章分支 + 硬约束 + 反例。

---

## 适用范围：只管原创，不管编译类

下面的"声音"和"三种文章分支"只约束 **Kevin 原创文章**（他自己的判断、经验、实测）。

**编译/整理类**（比如 Postgres Weekly 周刊编译、外部资讯整理翻译、任何技术周刊汇总）**不归这个 skill 管，走 `newsletter-digest` skill**。判断标准不变：标题/frontmatter 带"编辑整理""周刊""汇编"这种字样，或内容是转述多个外部来源而不是 Kevin 自己的经历判断。拿不准就问一句，别自己套声音规则重写，也别自己临时处理编译类流程——`newsletter-digest` 已经内置了独立子agent核实、固定排版骨架、配图定制、自动校验重试这一整套，不用在这里重新走一遍。

编译类的写作规范细节（豁免声音规则、传播/技术媒体口吻要求、判断标准）都维护在 `newsletter-digest` skill 里，这里不重复。

## Kevin 的声音（原创文章适用，编译类不适用）

这四条是 Kevin 4 篇代表作里都成立的特征：

1. **第一人称，直接**——"我跑了""我翻了""我没想明白""我都试过最后都没留下"。不是"笔者"，不是"我们可以看到"。
2. **数据/事实先于解读**——先贴日志、SQL、命令、数字，再说"这意味着什么"。不要倒过来写。
3. **结尾给判断不给总结**——"装。但你要清楚自己买的是什么"、"AI 工具选什么不是关键"。不写"综上所述""通过以上分析"。
4. **段落标题用"一、二、三、四"**——Kevin 文风识别符。

---

## 开头：必须是钩子，不是定义

**硬约束：第一段三句话之内，读者必须能猜到这篇要说什么。**

不写导读、不写背景铺垫、不写"最近 X 圈很火..."、不引 README 自我介绍。

Kevin 实际用过的 4 种钩子，参考但不限定：

| 钩子类型 | 出处 | 示例 |
|---------|------|------|
| **对话钩子** | DBA 工具单 | "有人问我现在用什么 AI 工具。我说了之后他追了一句：那你用来干什么？" |
| **误导期待** | Headroom | "冲着 README 那张 60-95% 节省的表去装的 Headroom。跑了两天，翻日志的时候我就觉得不对。" |
| **经验断言** | 不用现成 AI 工具 | "我都试过，最后都没留下。" |
| **读者场景** | PostgreSQL 案例 | "很多人盯着 EXPLAIN 找问题..." |

**反例（禁止）**：
- ❌ "随着 AI 技术的发展..."
- ❌ "本文将介绍..."
- ❌ "X 是什么？为什么重要？" （设问式开头）
- ❌ "在开始之前，让我们先了解..."
- ❌ 直接复制 README 第一段当开头

## 三种文章分支

按内容自动判断走哪个分支。结构是参考，不是模板。

### 分支 A：GitHub 项目类

代表：[[Headroom OSS 默认配置实测]]

**必须做的**：
- **第一次提到项目时，必须给 GitHub 链接**（脚注或行内链接）。读者看完想去看项目，不能让他自己搜。
- 引 README 自己的描述说"它是什么"，别绕。
- 核心是**实测 vs 宣称的差距**，或**它戳到了什么真痛点**——而不是空泛的"它为什么火"。Headroom 那篇就是"35% 实测 vs 60-95% 宣称"做的核心。
- 用过：贴实测数字、命令、日志、踩的坑。
- 没用过：交代清楚"我还没用，凭读 README + issue + commits 的判断"，不装。

**结构是长出来的**，不是套出来的。可能 3 段可能 5 段，看内容。

### 分支 B：技术案例类

代表：[[explain 看起来正常，查询还是慢]]

**模板化最强的分支**。结构通常是：
- 表象（用户看到什么）
- 根因（贴 SQL/EXPLAIN/配置）
- 怎么判断（命令、指标）
- 解法

可以是单案例展开，也可以是多案例列表（PostgreSQL 那篇是 5 个反直觉案例并列）。

**硬约束**：
- 必须有具体可复现的代码/SQL/命令
- 不要只讲"原理"——读者要的是"我遇到这个怎么办"

### 分支 C：心得 / 工作方式类

代表：[[一个 DBA 的 AI 工具单]]、[[我为什么不用现成的 AI 写作工具]]

**结构最自由的分支**。常见骨架：
- 我在做什么
- 我为什么这么做（对比"别人怎么做"）
- 怎么验证 / 边界在哪里

**硬约束**：
- 不堆方法论。"分清楚 X 和 Y" 这种判断必须有具体场景支撑
- 必须有"对立面"——你说要做 X，是因为别人在做 Y、而 Y 有什么问题

### 分支 D（试行）：洞察分析类

**这个分支还没有 Kevin 亲自写过、发布过的代表作，规则是从一篇 AI 起草的测试文章里反推出来的，成熟度不如 A/B/C，先记下来，等 Kevin 真发过一两篇同类文章之后再补硬约束。**

适用场景：不实测、不复现代码，基于多方报道对一个事件/发布做判断（比如"这次发布说明了什么""这两件事放在一起意味着什么"）。跟分支A的区别：分支A即使"没用过"，核心仍然是这一个项目本身；这个分支的核心是"把几件独立发生的事放在一起看出的判断"，判断本身才是主角。

初步观察到的骨架：
- 摆出一个显眼的事实/数字，然后说"但更值得注意的是另一件事"（对照关系起手）
- 拆解"这件事是什么"，引官方定义
- 把"报道实际证实了什么"和"我自己的推测"分开写，不能让读者以为推测是报道的结论
- 结尾摆判断，如果判断的证据强度不够，要明确说"两种解释我都无法证伪"，不能硬装成一个更可信

## 溯源 / 参考资料

**位置：文章最后**，正文结尾段之后。

**格式：脚注**（`[^1]`、`[^2]`）。

**内容**：
- GitHub 项目类——项目仓库链接是 `[^1]`，必给
- 引用的官方文档、博客、论文——一条一个脚注
- 每个 URL 必须实际 fetch 验证过存在且指向正确内容

**不要**：
- 不要在文章中间散布"参考资料"小节
- 不要"延伸阅读"这种推荐式列表
- 不要写没访问过的 URL
- **不要在脚注列表后面再加一段斜体"说明/免责声明"式的收尾**（比如"本文未实际安装/运行……仅供参考"这类）。这类话术读起来像AI生成内容常见的安全声明尾巴，跟四篇代表作的收尾方式（一句话给判断，不加免责说明）不符。该交代的方法论限制（没实测、某处未逐字核实）拆开塞进对应脚注或正文对应段落里说清楚，不要单独开一段、单独换斜体字体

## 事实硬底线

- 所有数字、版本号、日期是动手核实过的（WebFetch 或本地实测），不是凭记忆写的
- 所有外链 URL 是实际 fetch 过的，不是猜的
- Kevin 的个人判断没伪装成外部事实
- 错信息比少信息更糟——找不到来源就删掉/改保守

**初稿写完后，必须有一遍独立的"脚注回查"，不能相信写的时候已经核对过。** 具体做法：逐条打开每个脚注对应的来源，把正文里那句话和来源原文并排看一遍，专门抓这两类问题——

1. 正文写的是"某个判断/关联/解读"，但脚注来源其实只是报了个事实，没做这个判断——这时候要么找到真的做了这个判断的来源，要么把它明确改写成"这是我自己的判断，来源本身没这么说"，不能让读者以为是外部结论。
2. 数字/措辞在转述过程中悄悄挪了位——比如把 A 来源的数字和 B 来源的评价拼成一句话，看起来是同一个信源说的，实际不是。

这一遍不是查"链接打不打得开"，是查"我写的这句话，来源真的这么说了吗"——研究阶段标注过的可信度不会自动带到写作阶段，草稿里的每句转述都要重新对一遍原文，不能凭研究简报里的印象直接写。

**这条对"独立审校/独立评审"给出的结论同样成立，不只是对自己写的初稿成立。** 找独立子agent复查是防"同模型自查看不见自己的错"这个问题的，但独立agent自己也会看错、编错——它说"来源A其实是这么写的"，这句话本身也要素材核实，不能因为它是"独立视角"给出的就直接采信、直接照改。别人的核查结论和自己的初稿一样，都只是"待核实的转述"，不是"已核实的事实"。
