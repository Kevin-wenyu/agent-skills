# newsletter-digest

## 这个 skill 的定位

把技术周刊/散装技术文章加工成公众号草稿，全程不需要中途确认（配图最终成品除外，见下）。
核心是用**独立子agent重新回源核实**取代同模型自审，因为 PG Weekly #656 已经证明后者会漏检真实错误。

只处理编译/汇总类内容。Kevin 自己原创的文章（他自己的判断/经验/实测）不归这个 skill 管，走 `write-article` skill。

---

## 输入分流

| 输入 | 行为 |
|------|------|
| 单条链接，没有额外说明 | 默认立即单篇出稿，跑完整条流水线 |
| 单条链接 + 明说"先存着"/"加入队列" | 追加进 `raw/newsletter-queue.md` 表格，不触发流水线 |
| "汇总一下"/"这期够了" | 读取 `raw/newsletter-queue.md` 所有行，喂给流水线，处理完后把对应行从队列删除 |
| 结构化周刊 URL（如 postgresweekly.com/issues/NNN） | 先 WebFetch 页面解析出所有子文章链接，当成一批处理 |

---

## 五段流水线

### 1. Generator：抽取，按分量分级

先通读来源，分类：

- **主故事**（有独立标题、有作者署名、值得深挖）——WebFetch 全文，抽取：英文原标题（不翻译）、作者、日期、核心论点、关键技术细节（版本号/命令/参数）、逐字引用（带引号，必须是抓下来的原文片段，不是转述）。每条标注来源 URL 作为锚点。
- **短链接/发布公告**（一句话带过的内容）——直接按来源自己的转述整理，不做深度抽取。

一次可以并行 WebFetch 多篇主故事（一条消息发多个 WebFetch 调用）。

### 2. Critic：独立复核，只对主故事级别做

对每个被标记为"主故事"的条目，用 `Agent` 工具派生一个独立 subagent（可并行派多个）。

**关键：这个 subagent 的 prompt 只包含原始来源 URL，不包含 Generator 已经写好的草稿内容。** 让它自己重新 WebFetch、独立抽取一遍同样的字段（核心论点/关键技术细节/逐字引用）。subagent 交回结果后，再在主线程里跟 Generator 的版本做 diff。

短链接/发布公告级别的条目不派 Critic——出错空间小，独立重抓的 token 成本不划算。

**diff 出的不一致，统一自动降级处理，不中断流程：**

- 具体数字/版本号对不上 → 去掉数字，改定性描述
- 术语用词跟原文不完全一致 → 改用原文的确切措辞
- 状态类描述有差异（"已合并"/"提案中"/"讨论中"这类）→ 以 Critic 独立抓到的原文状态为准，这类错误历史上最容易误导读者，优先级最高
- Critic 完全找不到某个技术细节的原文依据 → 整条从草稿里删掉，不是硬留着改保守说法

每处降级/删改都记一行到风险清单（给 Kevin 看的那份，见下方"交付"）。

### 3. 排版：固定骨架，不引入新事实

**output 报告（`output/学习/`）和公众号文章（`raw/articles/`）总览的格式不一样，不能混用**——这条是从 #660 那次的真实事故里补的教训：output 报告可以用 markdown 表格当总览（给 Kevin 看，宽表格没问题）；**公众号文章的总览必须是编号列表，不能是表格**（2026-07-30 已经踩过一次坑：表格在手机端窄屏会断词，改成了编号列表，这条不是风格偏好，是硬约束）。

output 报告骨架（表格总览）：

```markdown
# {周刊名/主题} {期号或日期} 内容整理

本期主标题是"XXX"，主线是……

| 序号 | 内容 | 作者 / 来源 | 日期 | 主要讲什么 |
|---:|---|---|---|---|
| 1 | {英文原标题} | {作者} | {日期或 -} | {一句话} |
```

公众号文章骨架（编号列表总览，**多篇周刊模式必须有这一段，不能用配图顶替**；只有单篇模式才整段跳过直接进小节）：

```markdown
# {周刊名/主题} {期号或日期} 编辑整理

{封面图}

本期主标题是"XXX"，主线是……

**1. {英文原标题}**（{作者}，{来源}）—— {一句话描述}

**2. {英文原标题}**（{作者}，{来源}）—— {一句话描述}

...（每条主故事和简讯都要有一行，跟 output 报告表格里的行一一对应）

## {文章标题}

作者/来源：{作者}，{日期}

{如果这篇有专属插图/数据对比图，放在这里——紧跟在作者行后面，不是放在全文总览列表那个位置}

{核心论点一句话总起}

> "{逐字引用}"

{展开论述，带更多逐字引用和技术细节}

链接：{URL}
```

**总览列表和"某一篇的插图"是两个不同东西，不要用后者顶替前者**——总览列表的作用是让读者扫一眼知道这期有哪些内容，插图的作用是帮读者理解某一篇的核心机制/数据，图再好也不能替代总览，两个都要有。

**硬约束：每篇/每条必须独立成一个 `##` 小节，链接紧跟在它自己后面**，不能把多个条目堆在一个大标题下、末尾甩一个统一链接列表（`publish.py` 用的 python-markdown 会把"说明文字后紧跟不留空行的列表"塌陷成一段，链接全挤一行；`check.py` 的 `check_section_links` 会对这种情况报 warning）。

编译类文章不套 `write-article` 的 Kevin 声音/钩子/A-B-C 分支规则，但要有传播/技术媒体口吻——开篇和过渡段不要为了"显得有洞察"硬造统一比喻，有共性就直说是什么共性，没有就分开讲清楚。

Frontmatter：

```yaml
---
title: {标题}
date: {YYYY-MM-DD}
tags: [{相关领域}, 整理]
status: draft
---
```

### 4. 配图：定制设计，自查后仍需 Kevin 终审

用 `fireworks-tech-graph` skill。**不套固定模板**：

- 封面：用当期最有冲击力的数字/引用做视觉主体，不是回收固定吉祥物剪影
- 内容图（多篇模式）：按内容实际论证结构选形式（分层架构图/时间线/对比图），不是固定六边形辐射 mindmap
- 插图（可选）：只有某篇主故事适合用一张图讲清楚核心机制时才做

生成后自己把 SVG 转 PNG 检查有没有压字、有没有纯装饰不承载信息的元素，不行就重做——这轮自查不需要 Kevin 参与。

**但最终配图仍然是本流程唯一需要 Kevin 人工终审的部分**——上线前把图（或图的描述）单独指出来请 Kevin 看一眼，其余步骤全自动到底，不为图之外的内容打断流程。

### 5. 校验：自动重试，不出不合格版本

```bash
cd raw/publishing-pipeline
.venv/bin/python check.py "articles/路径/文章.md"
```

`check.py` 会跑：SVG 引用完整性、SVG width/height、SQL 块校验、讲次引用、frontmatter 完整性、小节链接完整性。

不过关自动修复对应部分重新生成，重试上限 2 次。超过上限仍未解决的，如实写进风险清单交给 Kevin，不做出一个"看起来过关"的假成品。

"封面文字跟标题关键词不完全对应"这类既有的良性误报警告可以忽略（`check_cover_title_sync`）。

---

## 交付

1. 排版好的成品文章（`raw/articles/ai-standalone/` 或 Kevin 指定目录，`status: draft`）
2. ≤5 行风险提示清单——哪些地方被 Critic 降级/删改、哪些校验重试过仍未完全解决
3. 一句话"这次运行自己调整了什么机制"（如果 Critic 判断规则或格式校验规则跑起来不合理，可以自己判断调整再重跑，但要如实告知调整了什么）
4. 单独指出配图需要 Kevin 看一眼确认

真正推到公众号发布仍然要 Kevin 明确说"发布"才跑 `publish.py`——这只是把内容推到 WeChat 草稿箱，Kevin 还要去公众号后台手动确认发布。

---

## 草稿覆盖策略

同一篇文章重新跑流水线，如果新产出比旧草稿更合适，直接覆盖或删除旧版本重来，不需要检测是否被手动改过、不需要暂停确认（2026-07-30 Kevin 明确拍板）。
