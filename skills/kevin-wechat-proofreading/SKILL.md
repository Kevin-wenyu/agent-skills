# 公众号AI味+细节审校

## 这个 skill 做什么

对 `write-article` 写完的初稿做两遍复查：AI味扫查、阅读细节打磨。每条问题带具体改法，不擅自改定稿。**不查事实**——数字/日期/引用来源的核实是 `write-article` 的"事实硬底线"和发布前 `check.py` 已经管的事，这里再查一遍是重复劳动。

## 为什么必须用独立子agent

`write-article` 写初稿时脑子里已经装满了这篇文章想怎么写、为什么这么写。让同一个上下文回头检查自己刚写的东西，容易对自己的措辞视而不见——这是`newsletter-digest`独立子agent核实设计已经验证过的问题：同模型自查会漏掉一份全新上下文一眼就能看到的错误。

所以执行这个skill时，用 Task 工具起一个独立子agent去读文章全文，不要把写作过程中的对话历史带过去——子agent只应该看到"这是一篇写完的文章"，不知道写作时纠结过什么。

## 判断标准：Kevin的声音，不是通用AI检测清单

不用"AI味"的通用定义去挑毛病。标准是`write-article`里定义的东西：

- 4条声音特征（第一人称直接、数据先于解读、结尾给判断不给总结、"一二三四"标题）
- 开头钩子的反例清单（❌"随着AI技术的发展..."、❌"本文将介绍..."等）——**这份清单原本只管开头，这个skill要把同样的判断标准用到全文**，不只是第一段
- 三种文章分支各自的硬约束（有没有堆方法论、有没有对立面、有没有具体代码支撑）

一句话判断法：这段读起来像不像"Kevin亲口说的"，还是像"任何一个技术公众号都能发的"。

## 执行步骤

### 第一遍：AI味扫查

逐段检查这几类问题（这份清单会随实际写作暴露的新问题持续更新，不是一次定死）：

- **套话词汇**——说白了、简单来说、换句话说、不可否认、毫无疑问、值得注意的是。**但要分清楚这个词后面有没有真的在做事**：如果删掉这个词、句子意思完全不变，是空转的套话，删；如果这个词后面紧跟着一句把前面的术语/引用真的翻译成大白话（比如"简单说，就是不把功能都绑死在coding agent里"），这是在做真正的转译工作，不是套话，别删——跟下面"句子节奏"那条不能打架。
- **一句话塞太多信息，没有喘气的地方**——这是比上面那条更根本的问题：一句话里把"叫什么名字+引用定义+解释"这类2-3件不同的事硬连起来，没有停顿，也没有转折词。**别只搜冒号/分号**——这条第一次实跑时就是这么漏检的：只查了带冒号的句子，漏了一句纯粹用逗号连起来的三段式（"很像，谁更彻底，两边都没读过，说不好"）。冒号只是这个问题最显眼的一种写法，纯逗号堆句子是同一个毛病，检查时不能靠搜某个标点符号，要数这句话里实际塞了几件不同的事——2件以上、又没有停顿，不管用什么标点连的都算。改法不是删字，是**拆句**：在自然的概念边界处断成几句话（句号，不是冒号），并且在从"引用/术语"转到"解释"的地方，看要不要加一个"简单说，就是""说白了""换句话说"这类真正在做转译工作的过渡词——不是每处转折都要加，但一整段又长又密、完全没有这类过渡词的，要重点看。参照 write-article 里"句子节奏"那节的反例/正例对照。
- **排比升华句**——"不仅是...更是..."、"不仅...而且...更..."这类总结式排比。
- **"A不是B，是C"对照句**——跟上面那条是两回事，这个更隐蔽：单看每一处都成立，但全文用超过3-4次就会形成一种可辨认的"AI腔"节奏。**这一条也要用 grep 数一遍"不是"出现的次数**再判断，不能靠读的时候的印象，第一次实跑时全文用了8-9次没被通读发现是"整体偏多"，是事后数出来的。改法不是每处都删掉"不是"，是挑几处改成别的句式（比如"这不是A是B"→"目标是B，A用不上"这种换个说法），保留1-2处最有力的。
- **标点习惯**——破折号全篇控制在1-2处以内；「」引号不过度使用。**这一条必须用 grep 之类的工具数一遍实际出现次数，不能靠读的时候数**——第一次实跑时读一遍数出5处，实际是8处，漏了3处没被通读发现，靠肉眼数可数类问题不可靠。
- **机械三段式**——每段都是"观点+例子+总结"的固定结构，读起来像模板。
- **开头钩子失效**——对照 write-article 的反例清单重新看一遍第一段，不只是写的时候判断过就算了，写完之后的第一段有时候会悄悄漂回套路。
- **诚实免责句式被复用成模板**——write-article 鼓励"没测过就说没测过"，但这个诚实动作本身如果每次都用同一个句式模板（"没...过...不装"这种）反复触发，读者感受到的不是诚实，是"这篇文章在固定间隔插入同一段免责声明"，比不诚实还像AI写的。**全文 grep 一遍类似"不装""说不出来""给不出"这类诚实标注收尾词，超过2次要看是不是在重复同一个句式**，是的话只留最必要的一处，其余的改写成不同的说法或者直接并进上下文，不单独起一句。这条第一次实跑时漏了——"没装过...不装"这个模板在同一篇里连用了两次，读起来像固定套话。

每处标记必须给出具体的改写版本，不能只说"这里AI味重"。

### 第二遍：细节打磨

- 标题是否有吸引力，是否符合 topic-gen 阶段定的标题公式
- 开头三句话能不能留住读者
- 段落长度是否适合手机阅读——单段不超过4-5行
- 有没有可以删掉的冗余句子
- 三种文章分支各自的硬约束有没有漏掉（比如GitHub项目类是否给了仓库链接、技术案例类是否有可复现代码）
- **回指清晰度**——结尾段/后段提到前文讲过的概念时，有没有省略掉关键限定词，导致单独摘出这一句读会产生歧义或指代不明。结尾段风险最高，因为读者经常跳读只看结尾，读到时早忘了前面铺垫过什么，"这个""涨价""它"这类回指词必须还原成具体名词才安全。**这不是查事实**（事实本身在前文可能已经交代清楚、有脚注），是查这一句话单独拎出来读还站不站得住
- **缺主语/归属不明**——这是回指清晰度里最容易漏看的一种，不是模糊代词，是整句话干脆没写主语。中文允许省略主语，段落内部靠上下文补全没问题，但一旦一段话里同时涉及多个行动者（比如"公司做了X""媒体说了Y""我认为Z"混在一起），任何一句省略主语的话都要重新读一遍，明确这句到底是谁做的/谁的东西——尤其"某产品/某价格是谁的"这种归属信息（"V4-Pro是DeepSeek自己的模型"这种），第一次实跑时改了两轮才补全，说明这条不能只查一遍就算完，每处省略主语的分句都要单独过一遍

## 改写建议本身也要读一遍，不能只满足检查项

这条适用于两遍里给出的每一条改写建议，不是单独一步。

清单能告诉你"缺了什么"（缺主语、有套话、破折号超标），但补上去不等于补好了——把缺的词硬塞回句子里，检查项满足了，句子可能还是生硬的，读起来像打了个补丁。第一次实跑时就出过这个情况：给一句话加了"主语"和"归属"两个词，结构上不缺东西了，但整句话读起来别扭，又被指出来重写了一遍。

所以每条改写建议写完之后，**把改完的完整句子当成第一次看到它的读者，从头读一遍**，问自己："这是自然写出来的一句话，还是明显能看出中间插了个词进去？"如果读起来别扭，不要满足于"检查项过了"，要把整句甚至整段重新组织，而不是在原句基础上打补丁。文章里如果前面已经出现过表达同一类意思的自然句式（比如"一边...一边..."这种并列结构），后面遇到同类问题优先复用那个句式，不要每处都重新造一个新说法。

```
## 第一遍·AI味
- [位置] 问题 → 建议

## 第二遍·细节
- [位置] 问题 → 建议
```

## 参考示例

```
## 第一遍·AI味
- [第3段第1句] "说白了，这个功能就是让AI记住你的习惯。" → 删掉"说白了"，直接说"这个功能让AI记住你的习惯。"
- [第5段] 整段是"观点+例子+总结"机械三段式，读起来像模板 → 删掉总结句，让例子本身说话

## 第二遍·细节
- [第2段] 单段8行，手机上要滑两屏 → 从"另外"处断开分成两段
```

## 边界

- 不查事实、不核实链接、不判断数字对不对——这些是 write-article 和 check.py 的职责。
- 只提出修改建议，不擅自替用户改定稿，除非用户明确说"直接改"。
- 判断标准是 write-article 定义的 Kevin 声音，不是通用 AI 检测规则——如果某处读起来"AI味重"但其实符合 Kevin 一贯的表达习惯，不要为了合规而改。
- 这份AI味清单是起点，用几次之后如果发现某类问题反复出现但清单没覆盖到，应该更新这个 SKILL.md 本身。
