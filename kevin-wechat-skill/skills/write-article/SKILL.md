# 公众号原创文章写作

## 首次使用前必做：这份 skill 是带真人校准的参考实现，不是空模板

下面"Kevin 的声音"和"锚点文章"两节，是这个 skill 原作者（Kevin）用自己 4 篇真实代表作校准出来的具体规则——保留真实内容是故意的：抽象的"保持自然""语言简洁"这类规则AI执行不了，具体到"用了什么钩子、几个字、举了哪句原话"才执行得动。

但这两节对你没用，因为那是别人的声音。**装上这个 skill 后，第一件事是把"Kevin 的声音"和"锚点文章"替换成你自己的**：挑 3-4 篇你自己写得最满意、最像"你"的文章，跟着"Kevin 的声音"那节的四条格式，提炼出你自己的等价规则；锚点文章列表换成你自己那几篇的路径。三种文章分支、钩子类型、事实核查、发布清单这些结构性的部分不用动，换了声音之后照样成立。

## 这个 skill 的定位

**记住你怎么写，确保 AI 不要写歪。**

不规定段数、图数、结构模板。不写"做这些/禁止这些"的风格规则。
靠四件东西：跨类型的声音特征 + 三种文章分支 + 硬约束 + 反例。

---

## 适用范围：只管原创，不管编译类

下面的"声音"和"三种文章分支"只约束**原创文章**（作者自己的判断、经验、实测）。

**编译/整理类**（比如技术周刊编译、外部资讯整理翻译、任何技术周刊汇总）**不归这个 skill 管，走 `newsletter-digest` skill**。判断标准不变：标题/frontmatter 带"编辑整理""周刊""汇编"这种字样，或内容是转述多个外部来源而不是作者自己的经历判断。拿不准就问一句，别自己套声音规则重写，也别自己临时处理编译类流程——`newsletter-digest` 已经内置了独立子agent核实、固定排版骨架、配图定制、自动校验重试这一整套，不用在这里重新走一遍。

编译类的写作规范细节（豁免声音规则、传播/技术媒体口吻要求、判断标准）都维护在 `newsletter-digest` skill 里，这里不重复。

## Kevin 的声音（参考实现，请替换成你自己的——见上方"首次使用前必做"）

这四条是 Kevin 4 篇代表作里都成立的特征：

1. **第一人称，直接**——"我跑了""我翻了""我没想明白""我都试过最后都没留下"。不是"笔者"，不是"我们可以看到"。
2. **数据/事实先于解读**——先贴日志、SQL、命令、数字，再说"这意味着什么"。不要倒过来写。
3. **结尾给判断不给总结**——"装。但你要清楚自己买的是什么"、"AI 工具选什么不是关键"。不写"综上所述""通过以上分析"。
4. **段落标题用"一、二、三、四"**——Kevin 文风识别符，换成你自己的标志性习惯。

## 开头：必须是钩子，不是定义

**硬约束（这条是结构性的，不用换）：第一段三句话之内，读者必须能猜到这篇要说什么。**

不写导读、不写背景铺垫、不写"最近 X 圈很火..."、不引 README 自我介绍。

Kevin 实际用过的 4 种钩子，作为参考实现，帮你理解"钩子"这个概念该具体到什么颗粒度——类型可以保留，例句请换成你自己文章里的：

| 钩子类型 | 出处（Kevin的例子，请替换） | 示例 |
|---------|------|------|
| **对话钩子** | DBA 工具单 | "有人问我现在用什么 AI 工具。我说了之后他追了一句：那你用来干什么？" |
| **误导期待** | Headroom | "冲着 README 那张 60-95% 节省的表去装的 Headroom。跑了两天，翻日志的时候我就觉得不对。" |
| **经验断言** | 不用现成 AI 工具 | "我都试过，最后都没留下。" |
| **读者场景** | PostgreSQL 案例 | "很多人盯着 EXPLAIN 找问题..." |

**反例（禁止，结构性，不用换）**：
- ❌ "随着 AI 技术的发展..."
- ❌ "本文将介绍..."
- ❌ "X 是什么？为什么重要？" （设问式开头）
- ❌ "在开始之前，让我们先了解..."
- ❌ 直接复制 README 第一段当开头

## 三种文章分支（结构性，不用换，代表作例子请替换）

按内容自动判断走哪个分支。结构是参考，不是模板。

### 分支 A：GitHub 项目类

代表：Kevin 的《Headroom OSS 默认配置实测》（换成你自己同类型的代表作）

**必须做的**：
- **第一次提到项目时，必须给 GitHub 链接**（脚注或行内链接）。读者看完想去看项目，不能让他自己搜。
- 引 README 自己的描述说"它是什么"，别绕。
- 核心是**实测 vs 宣称的差距**，或**它戳到了什么真痛点**——而不是空泛的"它为什么火"。
- 用过：贴实测数字、命令、日志、踩的坑。
- 没用过：交代清楚"我还没用，凭读 README + issue + commits 的判断"，不装。

**结构是长出来的**，不是套出来的。可能 3 段可能 5 段，看内容。

### 分支 B：技术案例类

代表：Kevin 的《explain 看起来正常，查询还是慢》（换成你自己同类型的代表作）

**模板化最强的分支**。结构通常是：
- 表象（用户看到什么）
- 根因（贴代码/日志/配置）
- 怎么判断（命令、指标）
- 解法

可以是单案例展开，也可以是多案例列表。

**硬约束**：
- 必须有具体可复现的代码/命令
- 不要只讲"原理"——读者要的是"我遇到这个怎么办"

### 分支 C：心得 / 工作方式类

代表：Kevin 的《一个 DBA 的 AI 工具单》《我为什么不用现成的 AI 写作工具》（换成你自己同类型的代表作）

**结构最自由的分支**。常见骨架：
- 我在做什么
- 我为什么这么做（对比"别人怎么做"）
- 怎么验证 / 边界在哪里

**硬约束**：
- 不堆方法论。"分清楚 X 和 Y" 这种判断必须有具体场景支撑
- 必须有"对立面"——你说要做 X，是因为别人在做 Y、而 Y 有什么问题

## 溯源 / 参考资料

**位置：文章最后**，正文结尾段之后。

**格式：脚注**（`[^1]`、`[^2]`）。

**内容**：
- GitHub 项目类——项目仓库链接是 `[^1]`，必给
- 引用的官方文档、博客、论文——一条一个脚注
- 每个 URL 必须实际 fetch 验证过存在且指向正确内容

**不要**：
- 不要在文章中间散布"参考资料"小节
- 不要"延伸阅读"这种推荐式列表
- 不要写没访问过的 URL

## 事实硬底线

- 所有数字、版本号、日期是动手核实过的（WebFetch 或本地实测），不是凭记忆写的
- 所有外链 URL 是实际 fetch 过的，不是猜的
- 个人判断没伪装成外部事实
- 错信息比少信息更糟——找不到来源就删掉/改保守

详细的事实核查流程和权威信息源清单，见 `../publish/references/fact-checking.md`。

## 发布清单

发前过一遍，每条不过就不发。基础检查交给 `publish` skill 处理（见下），这里列的是写作阶段要保证的前置条件：

**文件**
- frontmatter 有 `title` `date` `tags` `status: draft`
- H1 标题和 frontmatter `title` 一字不差
- GitHub 项目类：仓库链接在脚注里有

**图**
- 所有图都是校验过的合法 SVG
- 没有 Mermaid
- 浅底文字用深色（Kevin 的参考值：文字 `#1A1A1A`，浅底填充不浅于 `#C5C2F5` / `#B8E8D4`，仅供参考，换成你自己的配色规范）

**校验与发布**——调用 `publish` skill，不要在这里重新实现校验/发布逻辑。`publish` skill 会跑格式校验、SVG检查、发布前清单，通过后才会推草稿。
